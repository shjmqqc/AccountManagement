# Windows 自动更新部署

下文以首版 1.1.0 为例。更新地址由 `appsettings.json` 的 `UpdateUrl` 指定，例如 `https://downloads.example.com/updates/windows/`；留空关闭更新。部署前见[配置说明](../docs/deployment-settings.md)，已有安装建议使用用户目录配置以跨升级保留。
服务器目录：`./updates/windows`。仅部署静态文件，无需修改 Java 或数据库，也无需重载 Apache。

## 第一次发布

1. 使用 `desktop/release.ps1` 生成的 `desktop/artifacts/releases/1.1.0/` 文件。
2. 先上传该目录的 `*-full.nupkg` 和 `*-Setup.exe` 到服务器更新目录。
3. 完整上传 `releases.win.json.sig` 和 `releases.win.json`（可以先使用 `.tmp` 后缀，再逐个改名）。这两个文件必须来自同一次构建，内容不能手工编辑。更换过程中暂时不匹配会拒绝检查，完成后重试即可。
4. 保证目录可以遍历、文件可由 Apache 读取。更新程序不需要写网站目录；不要给网站进程额外的写权限。
5. 用户退出旧解压版，首次手动运行 `Shjmqqc.AccountManagement-win-Setup.exe`，以后从安装后的快捷方式打开。

也可以将生成的 `AccountManagement-update-server-1.1.0.zip` 在本地解压后上传其中三个文件（先 nupkg、后 JSON 和签名）。安装标识是 `Shjmqqc.AccountManagement`，与原登录状态目录 `%LOCALAPPDATA%/AccountManagement` 分开，避免安装/卸载覆盖登录文件。

首次安装包请通过可信渠道交付，例如由发布者提供本地生成的安装文件；HTTP 下载的首个安装包本身尚没有已安装客户端替它验签。后续应用内更新由客户端内置公钥验证。

运行时行为：启动后台检查；登录页及“帐户 → 检查更新”可手动操作。下载完成后必须点击“重启并更新”并确认。编辑/管理窗口打开时不能从主窗口发起更新；会话文件保留，不重建密码库。网络或签名校验失败不影响正常使用。旧的普通 ZIP/开发版提示先安装 Setup，不在任意文件夹直接覆盖程序。

## 发布后续版本

在 Windows 的 PowerShell 7.2 或更高版本中，从项目根目录执行：

```powershell
./desktop/test.ps1
./desktop/release.ps1 -Version 1.1.1 -Notes 'F:/完整路径/本次更新说明.md'
```

每次提高版本号，不能覆盖已发布版本。源码 `Version` 默认用于开发，发布脚本会为本次产物设置传入版本。首版使用完整更新包，暂不生成差分包。

上传顺序仍是包在前、清单和签名在后。保留旧版本包以照顾已检查出旧版本但尚未下载的客户端。首次安装的 1.1.0 对着服务器 1.1.0 清单显示“当前已是最新版本”，属于正常结果。

新版本若依赖服务端接口或数据库迁移，先升级后端再发布客户端。自动更新仅更新 Windows 文件，不自动升级服务器。

## 签名密钥

- `AccountManagement/UpdatePublicKey.pem` 是公钥，编译进客户端，可以提交 Git。
- 私钥默认在项目 `.tools/update-signing/private.dpapi`，仅在发布电脑保存，使用 Windows 当前用户 DPAPI 加密，不进入 Git、安装包或服务器。
- 发布脚本先确认私钥与公钥一致，使用 RSA-PSS/SHA-256 签名原始清单。客户端验签后读取版本及 SHA-256，下载后核对包哈希，重启前再次检查。丢失签名或包被修改都会拒绝更新。
- 已发布后不要重新运行密钥初始化来换钥。保留原 Windows 用户环境和密钥的安全备份；DPAPI 文件单独复制到另一台电脑通常不能解密，迁移发布环境需单独安排密钥迁移。
- 开源项目的其他部署者须使用自己的密钥和更新地址。初始化脚本只用于首次建立新发布身份，不能替代现有部署的密钥迁移。

发布签名不是 Windows Authenticode 签名。当前 Setup 未做代码签名，Windows 仍可能显示发布者/SmartScreen 提示。HTTP 不提供隐私保护，也不能防止阻断更新或回放旧的有效清单；客户端默认不降级。迁移 HTTPS 时修改 `appsettings.json` 的 `UpdateUrl` 并重启应用，无需修改代码。

## 验收

先以测试帐号安装旧版，发布更高版本，检查提示、下载、取消、确认重启、版本提升及登录状态保留。另测断网、缺失签名、改动清单、改动包，应保持旧版可用且不执行被修改的内容。

不要通过关闭验签或忽略错误解决服务器文件不匹配；重新上传同一次构建的文件即可。
